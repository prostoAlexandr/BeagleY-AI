# Шаг 1: Конфигурация Device Tree Overlay для LCD1602 (BeagleY-AI)

## 1. Поиск аппаратной метки шины (Target)

Для привязки устройства к физической шине `i2c-1` определяем имя её метки в дереве устройств:

1. Узнаем адрес памяти для логической шины `i2c1`:
   ```bash
   cat /sys/firmware/devicetree/base/aliases/i2c1; echo
   ```
   *Результат содержит адрес памяти:* `4900000`.

2. Находим имя метки контроллера по адресу `4900000`:
   ```bash
   grep -rn "4900000" /sys/firmware/devicetree/base/__symbols__/
   ```
   *Вывод:* `/sys/firmware/devicetree/base/__symbols__/mcu_i2c0`  
   *Итоговый target:* **`mcu_i2c0`**.

## 2. Исходный код оверлея (`lcd1602_overlay.dts`)

### Что такое формат .dtbo?
- DTS (Device Tree Source): Текстовый файл с исходным кодом описания железа.

- DTB (Device Tree Blob): Скомпилированный бинарный файл полного дерева устройств всей платы.

- DTBO (Device Tree Blob Overlay): Бинарный файл-«патч».

Вместо того чтобы перекомпилировать огромное базовое дерево всей платы BeagleY-AI при подключении каждого нового датчика или экрана, пишется небольшой оверлей (.dtbo). Загрузчик (U-Boot) берет базовый DTB и «накладывает» на него этот оверлей прямо в оперативной памяти перед стартом ядра.

### Что значит fragment@0?
Структура оверлея состоит из одного или нескольких фрагментов (fragment@0, fragment@1 и т.д.). Каждая секция fragment@X — это отдельное изменение/добавление в дерево.

Каждый фрагмент содержит две обязательные вещи:

1. `target` (или `target-path`): указывает место в базовом дереве, куда нужно внедрить изменения (в нашем случае target = <&mcu_i2c0>).

2. `__overlay__`: блок со свойствами и новыми узлами, что именно нужно вклеить в указанный target.

### Что такое status = "okay"
Добавить `status = "okay";` в узел устройства — хорошая практика для явного указания намерений.

1. Поведение по умолчанию: В спецификации Device Tree любой новый дочерний узел, у которого явно не задано свойство status, ядром Linux по умолчанию трактуется как активный (status = "okay"). Поэтому для вновь создаваемого узла lcd1602@27 ядро в любом случае вызывает probe().

2. Когда status = "okay"; обязателен: Это свойство необходимо писать тогда, когда узел уже существует в базовом .dtb, но по умолчанию отключён (status = "disabled";) — например, сам контроллер I2C на уровне процессора. В этом случае оверлей используется для перевода состояния из disabled в okay.

### Почему закомментированы address-cells и size-cells?
Символ # в файлах Device Tree (.dts) НЕ является знаком комментария!
Комментарии в .dts пишутся традиционно для C/C++: // комментарий или /* комментарий */. Символ # — это часть официального имени свойства в спецификации Device Tree.

Вот что значат эти строки для шины I2C:

- `#address-cells = <1>;` — сообщает ядру, что для описания адреса каждого дочернего устройства на этой шине используется одно 32-битное число (cell).
- `#size-cells = <0>;` — сообщает ядру, что устройства на этой шине не имеют диапазона/размера занимаемой памяти (размер равен 0).

Благодаря этим двум свойствам ядро понимает, как правильно прочитать следующую строчку в описании нашего экрана: `reg = <0x27>;`
Ядро смотрит на `#address-cells = <1>` и понимает, что 0x27 — это и есть тот самый 1 элемент адреса I2C-устройства.

### Что значит compatible = "custom,lcd1602-marquee"?
Строка compatible — это главный связующий идентификатор между железом в Device Tree и C-кодом драйвера в ядре. По общепринятому стандарту Linux строка записывается в формате "производитель,модель" (vendor,device). Префикс custom (или любой другой, например ti, raspberrypi) показывает «условного производителя».

Когда ядро Linux сканирует дерево устройств, оно берет эту строку custom,lcd1602-marquee и ищет в оперативной памяти загруженный драйвер, у которого в таблице of_device_id прописана точно такая же строка. Как только находит — вызывает функцию probe() этого драйвера.

## 3. Компиляция и установка

1. Скомпилировать `.dts` в бинарный оверлей `.dtbo`:
   ```bash
   dtc -I dts -O dtb -o lcd1602.dtbo lcd1602-overlay.dts
   ```

2. Скопировать оверлей в системную директорию:
   ```bash
   sudo cp lcd1602.dtbo /boot/firmware/overlays/
   ```

3. Прописать оверлей в конфигурационном файле загрузчика `/boot/firmware/extlinux/extlinux.conf`:
   ```text
   fdtoverlays /overlays/lcd1602.dtbo
   ```

4. Перезагрузить плату:
   ```bash
   sudo reboot
   ```

## 4. Проверка создания устройства

После перезагрузки выполнить 2 команды проверки:

1. **Проверка наличия узла устройства в sysfs на шине `i2c-1`:**
   ```bash
   ls -l /sys/bus/i2c/devices/1-0027
   ```
   *Ожидаемый результат:* Отображение символической ссылки на устройство `1-0027`.

2. **Проверка строки совместимости (`compatible`):**
   ```bash
   cat /sys/bus/i2c/devices/1-0027/of_node/compatible
   ```
   *Ожидаемый результат:* `custom,lcd1602-marquee`

# Шаг 2: Скелет I2C-драйвера и проверка функции probe()

## 1. Исходный код драйвера (`lcd1602_v1_skeleton.c`)

* **Разделение Устройства (Device) и Драйвера (Driver):** Ядро Linux чётко разграничивает информацию об оборудовании (Device Tree) и логику работы с ним (Driver). Драйвер регистрирует свои возможности в подсистеме I2C, а ядро автоматически сопоставляет их при появлении оборудования.
* **Связывание (Matching & Binding):** Процесс, при котором `i2c_core` находит соответствующий драйвер для устройства и вызывает функцию `.probe()`.
* **Контекст выполнения probe/remove:** Выполняются в **Process Context**. Внутри `.probe()` и `.remove()` разрешено усыплять процесс (`msleep`), выделять память (`kmalloc` с `GFP_KERNEL`) и выполнять синхронные I2C-транзакции.
* **Логирование через `pr_info` vs `dev_info`:**
  В представленном скелете используется `pr_info`. Однако в промышленном коде драйверов принято использовать `dev_info(&client->dev, "...")`, так как это автоматически добавляет в dmesg имя и адрес конкретного устройства на шине.

```c
/* 1. Таблица сопоставления Device Tree (Open Firmware) */
static const struct of_device_id lcd1602_of_match[] = {
    { .compatible = "custom,lcd1602-marquee" },
    { } // Нулевой терминатор (sentinel value)
};
MODULE_DEVICE_TABLE(of, lcd1602_of_match);

/* 2. Структура драйвера шины I2C */
static struct i2c_driver lcd1602_driver = {
    .driver = {
        .name = "lcd1602_marquee",
        .of_match_table = lcd1602_of_match,
    },
    .probe = lcd1602_probe,
    .remove = lcd1602_remove,
};

/* 3. Макрос свертывания boilerplate-кода */
module_i2c_driver(lcd1602_driver);
// Автоматически разворачивается в:
static int __init lcd1602_driver_init(void) {
   return i2c_register_driver(THIS_MODULE, &lcd1602_driver);
}
module_init(lcd1602_driver_init);

static void __exit lcd1602_driver_exit(void) {
   i2c_del_driver(&lcd1602_driver);
}
module_exit(lcd1602_driver_exit);
```

## 2. Конфигурация сборки (`Makefile`)

### Концепция KDIR и зависимостей ядра
* **Назначение KDIR:** Указывает путь к сборочному дереву ядра (`kernel build tree` / `kernel headers`).
* **Роль в сборке:** Предоставляет заголовочные файлы (`<linux/module.h>`, `<linux/i2c.h>`), внутренний сборочный инструментарий `Kbuild` и конфигурацию ядра.
* **Кросс-компиляция:** Использование условного присваивания `KDIR ?=` позволяет менять целевое ядро без правки `Makefile`.

### Ключевые параметры команды make

* **`-C $(KDIR)`:** Переключает текущую рабочую директорию на каталог ядра и запускает оттуда корневой `Makefile` ядра.
* **`M=$(PWD)`:** Передаёт корневому `Makefile` путь к внешней (out-of-tree) директории с исходным кодом модуля.
* **`modules`:** Цель ядра, выполняющая последовательную компиляцию объектов, этап post-processing (`modpost`) и связывание итогового `.ko` файла.

# Шаг 3: Реализация I2C-обмена и инициализация HD44780

## 1. Исходный код драйвера (`lcd1602_v2_init.c`)

### Ограничение по выводам (Pinout)
Микросхема PCF8574T имеет всего 8 портов ввода-вывода (P0–P7). Для управления дисплеем HD44780 требуются не только линии данных, но и служебные сигналы:

- P0: RS (Register Select — выбор: команда или данные)
- P1: RW (Read/Write — обычно притянут к земле)
- P2: EN (Enable — стробирующий сигнал тактирования)
- P3: LED (Управление подсветкой экрана)
- P4–P7: Линии данных DB4, DB5, DB6, DB7

Для 8-битного режима экрану потребовалось бы 8 линий данных (DB0–DB7) и минимум 2 служебные линии (RS, EN) — итого 10 выводов. У PCF8574T их всего 8.

**Как работает полубайтовый (4-битный) режим**

Контроллер HD44780 аппаратного дисплея имеет встроенную поддержку 4-битного интерфейса. Любая передача 8-битной команды или символа разбивается на два последовательных полубайта (ниббла):
- Старший ниббл (биты 7–4): Передаются на пины P4–P7 вместе с флагами RS и LED. Подается импульс на EN для защёлкивания данных.
- Младший ниббл (биты 3–0): Сдвигаются на пины P4–P7 с теми же флагами. Подается второй импульс на EN.

Контроллер HD44780 на стороне экрана принимает эти два 4-битных фрагмента и автоматически собирает их во внутреннем буфере обратно в один 8-битный байт перед выполнением. (По самой шине I2C от BeagleY-AI к PCF8574T всегда передаются целые байты — каждый I2C-байт единовременно выставляет логические уровни сразу на всех 8 ногах P0–P7).

## 2. Функции задержки ядра (`<linux/delay.h>`)

В ядре Linux функции msleep и usleep_range из `<linux/delay.h>` предназначены для организации задержек выполнения кода с освобождением ресурсов процессора (переводом текущего процесса в состояние сна).

### `msleep(unsigned int msecs)`

**Что делает**: Переводит текущий поток в сон на указанное количество миллисекунд.

**Как работает**: Поток переводится планировщиком ядра в состояние сна (TASK_UNINTERRUPTIBLE), а процессор переключается на другие задачи (происходит контекстный переход). Реальная точность зависит от системного таймера ядра (CONFIG_HZ).

**Зачем нужен**: Используется для длительных задержек (обычно > 10 мс), где не требуется микросекундная точность. В коде инициализации HD44780 он нужен для паузы 50 мс после подачи питания и паузы 2–5 мс после команд сброса и очистки экрана (0x01).

### `usleep_range(unsigned long min, unsigned long max)`

**Что делает**: Переводит поток в сон на время в интервале от min до max микросекунд.

**Как работает**: Использует высокоточные таймеры ядра (hrtimers). Указание диапазона вместо фиксированного значения — главное требование ядра Linux для коротких задержек. Это позволяет планировщику объединять (батчить) прерывания таймеров от разных процессов в одну точку пробуждения, экономя ресурсоёмкие переключения CPU.

**Зачем нужен**: Используется для коротких паузовых интервалов (от 1 мкс до ~20 мс). В драйвере дисплея с его помощью формируется фронт стробирующего импульса Enable (линия E удерживается в 1 от 1 до 5 мкс, после чего опускается в 0) и выдерживается пауза 50–200 мкс для обработки полубайта контроллером PCF8574/HD44780.

| Функция | Диапазон времени | Механизм | В контексте прерываний / spinlock? |
| :--- | :--- | :--- | :--- |
| `udelay(us)` | < 10 мкс | Active-wait (цикл CPU) | **Да** |
| `usleep_range(min, max)` | 1 мкс – 20 мс | `hrtimers` (переход в сон) | **Нет** |
| `msleep(ms)` | > 10–20 мс | Планировщик (переход в сон) | **Нет** |

   ```

3. Выгрузка модуля (экран очистится, подсветка погаснет):

   ```

# Шаг 4: Файловый интерфейс /dev/lcd1602 (Character Device)

## 1. Концепция подсистемы miscdevice

Для предоставления пользовательскому пространству символьного устройства в `/dev/` используется легкая подсистема `miscdevice`:
* **Динамический minor-номер (`MISC_DYNAMIC_MINOR`):** ядро автоматически выделяет свободный номер устройства.
* **Права доступа (`.mode = 0666`):** разрешают запись и чтение без использования `sudo` или настройки внешних правил `udev`.
* **Безопасный обмен данными (`copy_from_user`):** корректно копирует данные из пространства пользователя (user-space) в буфер ядра (kernel-space).

## 2. Исходный код драйвера (`lcd1602_v3_cdev.c`)

### Что означает лицензия GPL

GNU General Public License (GPL) — это свободная лицензия с принципом copyleft («вирусная» лицензия). Она предоставляет пользователям четыре ключевые свободы: запускать код в любых целях, изучать и изменять его, распространять копии, а также публиковать модифицированные версии. Главное юридическое требование GPL: если вы создаёте производный продукт на базе GPL-кода или связываете свой код с ним и распространяете его, ваш итоговый код также обязан быть открыт и распространяться под лицензией GPL.

### Зачем макрос MODULE_LICENSE("GPL") нужен в коде драйвера

В контексте разработок под Linux этот макрос не просто юридическая формальность, а прямое техническое указание для компилятора и подсистемы загрузки модулей ядра (kmod / insmod):

- **Доступ к защищенным функциям ядра (EXPORT_SYMBOL_GPL):**
Сам Linux распространяется под лицензией GPLv2. Многие подсистемы ядра экспортируют свои внутренние функции и структуры через макрос EXPORT_SYMBOL_GPL(). Если в вашем модуле нет объявления GPL-совместимой лицензии, ядро блокирует доступ к этим символам на этапе загрузки или сборки.

- **Предотвращение «загрязнения» ядра (Kernel Tainting):**
Если загрузить модуль без указания GPL (или с указанием проприетарной лицензии), ядро установит системный флаг TAINT_PROPRIETARY_MODULE. Это сигнальное предупреждение в dmesg, указывающее, что в адресное пространство ядра загружен нетривиальный/закрытый код. Разработчики ядра Linux не принимают багрепорты и дампы упавших систем, если ядро отравлено проприетарными модулями.

- **Автоматическая документация и проверка:**
Инструменты сборки ядра (kbuild) используют значение MODULE_LICENSE, чтобы формировать служебную секцию .modinfo внутри .ko-файла. По ней система утилит определяет совместимость и легитимность модуля в рантайме.

Для модулей ядра допускаются и другие GPL-совместимые строки, например "GPL v2" или "Dual BSD/GPL", но короткая запись "GPL" является стандартом по умолчанию для большинства свободных драйверов.

# Шаг 5: Потокобезопасность и мьютексы

## Архитектурное обоснование (`lcd1602_v4_mutex.c`)

- **Защита от гонок и рассинхронизации протокола (Race Conditions):**
Дисплей работает в 4-битном режиме через I2C-расширитель PCF8574: передача одного байта требует двух полубайтов (nibbles) с тактированием строба Enable. Если два процесса одновременно запишут данные в /dev/lcd1602, их транзакции I2C перепутаются на уровне шины. Это приведет к рассинхронизации тетрад HD44780, выводу «мусора» на экран или заклиниванию контроллера дисплея.

- **Безопасное удаление модуля (Preventing Null Pointer Dereference / UAF):**
Если выгрузить модуль (rmmod) или отключить устройство в момент, когда поток пользовательского пространства выполняет write(), возникнет ситуация Use-After-Free или обращения по нулевому указателю. Мьютекс гарантирует атомарный сброс lcd_client = NULL и завершение текущих операций записи перед окончательной очисткой.

- **Корректная обработка сигналов ядра:**
Вызов mutex_lock_interruptible() вместо жесткой блокировки mutex_lock() позволяет процессу в user-space корректно прервать ожидание (например, по Ctrl+C / SIGINT), если шина I2C заблокирована другом потоком, не переводя процесс в незавершаемое состояние (Uninterruptible Sleep).

# Шаг 6: Архитектура отложенных работ (Workqueue & Delayed Work)

## 1. Контексты выполнения и подсистема Workqueue

В разработке драйверов ядра Linux существует строгое разделение контекстов:

* **User Context (Контекст системного вызова):** Код `lcd1602_write` выполняется в контексте потока пользовательского приложения (например, `echo`). Задержки и блокировки внутри `write()` заблокируют процесс пользователя.
* **Interrupt / Atomic Context (Контекст прерывания и таймеров):** Обычные таймеры ядра (`timer_list`) работают в атомарном контексте. В них **запрещено спать** (`msleep`) и захватывать мьютексы (`mutex_lock`). Попытка отправить данные по I2C из атомарного контекста приводит к **Kernel Panic**.
* **Kernel Thread Context (Контекст системных потоков):** Подсистема **Workqueue** передает выполнение функций фоновым системным потокам ядра (`kworker`). В контексте `kworker` код имеет право блокироваться, спать, выполнять I2C-транзакции и брать мьютексы без блокировки user-space.

## 2. Инициализация и макрос `INIT_DELAYED_WORK` (`lcd1602_v5_marquee.c`)

Структура `struct delayed_work` объединяет описатель работы (`struct work_struct`) и таймер ядра.

```c
INIT_DELAYED_WORK(&marquee_work, lcd1602_marquee_work_func);
```

* **Механизм:** Связывает экземпляр `marquee_work` с указателем на функцию-обработчик `lcd1602_marquee_work_func`.
* **Точка вызова:** Функция `probe()`. Это статическая инициализация при загрузке драйвера, подготавливающая внутренние указатели ядра (таймер при этом не запускается).

## 3. Планирование цикла (`schedule_delayed_work`)

Запуск фоновой работы в системной очереди `system_wq`:

```c
schedule_delayed_work(&marquee_work, msecs_to_jiffies(300));
```

* **Механизм работы:**
  1. Переводит миллисекунды (300 мс) в системные тики ядра (**jiffies**) с учетом частоты `HZ`.
  2. Ядро взводит таймер на указанный интервал.
  3. По истечении времени таймер помещает `marquee_work` в очередь системного потока `kworker`.
  4. Поток `kworker` просыпается и вызывает `lcd1602_marquee_work_func`.
* **Организация цикла:** Функция `lcd1602_marquee_work_func` в своем конце **повторно вызывает** `schedule_delayed_work()`, формируя асинхронный таймер прокрутки.

## 4. Синхронизация и остановка (`cancel_delayed_work_sync`)

Остановка цикла прокрутки при вызове `write()` или выгрузке модуля в `remove()`:

```c
cancel_delayed_work_sync(&marquee_work);
```

* **Механизм работы:**
  1. Отменяет взведенный таймер, если работа еще ожидает выполнения.
  2. **Синхронное ожидание:** Если `lcd1602_marquee_work_func` *уже исполняется* в контексте `kworker` на другом ядре CPU, вызов блокирует текущий поток до полного завершения воркера.
* **Назначение:**
  * В `write()`: Защита от race condition (старый воркер не перерисовывает экран во время записи нового текста).
  * В `remove()`: Защита от **Use-After-Free** и **Kernel Panic** (предотвращает вызов функции по адресу выгруженного модуля).

## 5. Алгоритм сдвига окна (Ring Buffer Window)

Логический сдвиг окна без перемещения данных в памяти:

```c
for (i = 0; i < DISPLAY_WIDTH; i++) {
    window[i] = marquee_buf[(marquee_pos + i) % marquee_len];
}
```

* **Принцип:** Буфер `marquee_buf` остается неизменным (`"TEXT   \0"`). Смещается только индекс `marquee_pos`.
* **Взятие по модулю (`% marquee_len`):** При выходе `marquee_pos + i` за пределы длины массива индекс автоматически сбрасывается в `0`, обеспечивая бесшовное закольцовывание.

# Шаг 7: Подсистема sysfs и виртуальные атрибуты устройств

## 1. Концепция и контексты
* **Назначение sysfs:** Предоставление интерфейса конфигурации (Control Plane) объектов ядра в пользовательском пространстве через виртуальную файловую систему (`/sys`).
* **Контекст выполнения:** Обработчики `show` и `store` выполняются в **Process Context**. Они могут усыплять процесс, захватывать мутексы и осуществлять синхронные блокирующие транзакции по шинам ввода-вывода (I2C/SPI).
* **Управление памятью буфера:** Функция `show` всегда получает выделенный ядром буфер размером `PAGE_SIZE` (4 KB). Запись возвращаемого значения производится строго через `sysfs_emit(buf, fmt, ...)`.

## 2. Макросы автоматизации и функции ядра (`lcd1602_v6_sysfs.c`)

```c
// 1. Создание структуры dev_attr_<name> с правами 0644 (Read/Write)
// Автоматически связывает функции <name>_show и <name>_store
DEVICE_ATTR_RW(name);

// 2. Объединение атрибутов в массив и генерация групп
static struct attribute *lcd1602_attrs[] = {
    &dev_attr_backlight.attr,
    &dev_attr_scroll_delay_ms.attr,
    NULL, // Массив должен завершаться NULL
};
ATTRIBUTE_GROUPS(lcd1602); // Создает lcd1602_groups

// 3. Автоматическая привязка к жизненному циклу устройства
static struct i2c_driver lcd1602_driver = {
    .driver = {
        .dev_groups = lcd1602_groups, // Ядро создаст файлы при probe и удалит при remove
    },
};
```

## 3. Безопасный парсинг данных из User Space

Для предотвращения уязвимостей типа Buffer Overflow и выхода за границы диапазонов используется встроенное API ядра:

```c
// Парсинг логических значений ("1", "0", "on", "off", "yes", "no")
int kstrtobool(const char *s, bool *res);

// Парсинг беззнаковых целых чисел с указанием системы счисления (10)
int kstrtouint(const char *s, unsigned int base, unsigned int *res);
```

## 4. Синхронизация и предотвращение Race Conditions

1. **Защита разделяемых ресурсов:** Переменные `backlight_enabled` и `scroll_delay_ms` читаются и изменяются из разных контекстов (Process Context sysfs-вызовов и Kernel Thread Context воркеров `delayed_work`).
2. **Атомарность изменения:** Все модификации состояния устройства и вызовы I2C-транзакций защищаются единым `lcd_mutex` во избежание коллизий пакетов на шине I2C.

# Шаг 8: Автозагрузка модулей ядра Linux (depmod, udev, systemd)

## 1. Концепция и механизмы автозагрузки

* **Статическая автозагрузка (`systemd-modules-load`):** Простая принудительная загрузка модуля по имени из `/etc/modules-load.d/*.conf` при старте `sysinit.target`.
* **Динамическая автозагрузка (`udev` + Device Tree):** Событийно-ориентированная загрузка. Ядро генерирует `uevent` с `MODALIAS` при обнаружении узла в Device Tree, а `udevd` сопоставляет его с нужным `.ko` файлом.

## 2. Механизм работы dynamic devicetree loading via `udev`

- [Загрузка ядра / U-Boot]
- [Парсинг Device Tree: узел с compatible = "custom,lcd1602-marquee"]
- [Ядро формирует kobject и отправляет uevent через netlink]  
-> MODALIAS=of:Nlcd_nodeT*Ccustom,lcd1602-marquee
- [Демон udevd перехватывает uevent]  
-> Ищет совпадение MODALIAS в /lib/modules/$(uname -r)/modules.alias
- [udevd вызывает: modprobe of:Nlcd_nodeT*Ccustom,lcd1602-marquee]  
-> modprobe загружает lcd1602.ko из /lib/modules/...

## 3. Индексация бинарных файлов модулей (`depmod`)

```c
// В коде драйвера экспортируется таблица устройств:
MODULE_DEVICE_TABLE(of, lcd1602_of_match);
```

1. **Секция `.modinfo`:** Макрос `MODULE_DEVICE_TABLE` помещает строки метаданных `compatible` в ELF-секции модуля.
2. **Команда `depmod -a`:** Сканирует `/lib/modules/$(uname -r)/`, читает `.modinfo` и формирует системные индексные файлы:
   * `modules.dep` — карта зависимостей между модулями.
   * `modules.alias` — сопоставление строковых `MODALIAS` с именами файлов драйверов.

## 4. Последовательность установки и размещения

```bash
# 1. Копирование модуля в системную директорию out-of-tree модулей
sudo mkdir -p /lib/modules/$(uname -r)/extra/
sudo cp lcd1602.ko /lib/modules/$(uname -r)/extra/

# 2. Пересчет зависимостей и регистрация алиасов
sudo depmod -a
grep "lcd1602" /lib/modules/$(uname -r)/modules.alias

# 3. Регистрация статического автозапуска (опционально)
echo "lcd1602" | sudo tee /etc/modules-load.d/lcd1602.conf
```

## 5. `insmod` vs `modprobe`

* **`insmod`:** Низкоуровневый системный вызов (`finit_module`). Принимает только абсолютный путь к `.ko` файлу. Не умеет разрешать зависимости и не использует `modules.dep`.
* **`modprobe`:** Высокоуровневая утилита. Принимает имя модуля или алиас, самостоятельно ищет файл в `/lib/modules/$(uname -r)/`, автоматически загружает все зависимые модули согласно `modules.dep`.
