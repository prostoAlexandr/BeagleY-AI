# Шаг 0: Конфигурация Device Tree Overlay для LCD1602 (BeagleY-AI)

## 1. Поиск аппаратной метки шины (Target)

Для привязки устройства к физической шине `i2c-1` определяем имя её метки в дереве устройств:

1. Узнаем адрес памяти для логической шины `i2c1`:
   ```bash
   cat /sys/firmware/devicetree/base/aliases/i2c1; echo
   ```
   *Результат содержит адрес памяти:* `4900000`.

2. Находим имя метки контроллера по адресу `4900000`:
   ```bash
   grep -rn "4900000" /sys/firmware/devicetree/base/__symbols__/
   ```
   *Вывод:* `/sys/firmware/devicetree/base/__symbols__/mcu_i2c0`  
   *Итоговый target:* **`mcu_i2c0`**.

## 2. Исходный код оверлея (`lcd1602_overlay.dts`)

### Что такое формат .dtbo?
- DTS (Device Tree Source): Текстовый файл с исходным кодом описания железа.

- DTB (Device Tree Blob): Скомпилированный бинарный файл полного дерева устройств всей платы.

- DTBO (Device Tree Blob Overlay): Бинарный файл-«патч».

Вместо того чтобы перекомпилировать огромное базовое дерево всей платы BeagleY-AI при подключении каждого нового датчика или экрана, пишется небольшой оверлей (.dtbo). Загрузчик (U-Boot) берет базовый DTB и «накладывает» на него этот оверлей прямо в оперативной памяти перед стартом ядра.

### Что значит fragment@0?
Структура оверлея состоит из одного или нескольких фрагментов (fragment@0, fragment@1 и т.д.). Каждая секция fragment@X — это отдельное изменение/добавление в дерево.

Каждый фрагмент содержит две обязательные вещи:

1. `target` (или `target-path`): указывает место в базовом дереве, куда нужно внедрить изменения (в нашем случае target = <&mcu_i2c0>).

2. `__overlay__`: блок со свойствами и новыми узлами, что именно нужно вклеить в указанный target.

### Что такое status = "okay"
Добавить `status = "okay";` в узел устройства — хорошая практика для явного указания намерений.

1. Поведение по умолчанию: В спецификации Device Tree любой новый дочерний узел, у которого явно не задано свойство status, ядром Linux по умолчанию трактуется как активный (status = "okay"). Поэтому для вновь создаваемого узла lcd1602@27 ядро в любом случае вызывает probe().

2. Когда status = "okay"; обязателен: Это свойство необходимо писать тогда, когда узел уже существует в базовом .dtb, но по умолчанию отключён (status = "disabled";) — например, сам контроллер I2C на уровне процессора. В этом случае оверлей используется для перевода состояния из disabled в okay.

### Почему закомментированы address-cells и size-cells?
Символ # в файлах Device Tree (.dts) НЕ является знаком комментария!
Комментарии в .dts пишутся традиционно для C/C++: // комментарий или /* комментарий */.

Символ # — это часть официального имени свойства в спецификации Device Tree.

Вот что значат эти строки для шины I2C:

`#address-cells = <1>;` — сообщает ядру, что для описания адреса каждого дочернего устройства на этой шине используется одно 32-битное число (cell).

`#size-cells = <0>;` — сообщает ядру, что устройства на этой шине не имеют диапазона/размера занимаемой памяти (размер равен 0).

Благодаря этим двум свойствам ядро понимает, как правильно прочитать следующую строчку в описании нашего экрана: `reg = <0x27>;`
Ядро смотрит на `#address-cells = <1>` и понимает, что 0x27 — это и есть тот самый 1 элемент адреса I2C-устройства.

### Что значит compatible = "custom,lcd1602-marquee"?
Строка compatible — это главный связующий идентификатор между железом в Device Tree и C-кодом драйвера в ядре.

По общепринятому стандарту Linux строка записывается в формате "производитель,модель" (vendor,device).

Префикс custom (или любой другой, например ti, raspberrypi) показывает «условного производителя».

Когда ядро Linux сканирует дерево устройств, оно берет эту строку custom,lcd1602-marquee и ищет в оперативной памяти загруженный драйвер, у которого в таблице of_device_id прописана точно такая же строка. Как только находит — вызывает функцию probe() этого драйвера.

## 3. Компиляция и установка

1. Скомпилировать `.dts` в бинарный оверлей `.dtbo`:
   ```bash
   dtc -I dts -O dtb -o lcd1602.dtbo lcd1602-overlay.dts
   ```

2. Скопировать оверлей в системную директорию:
   ```bash
   sudo cp lcd1602.dtbo /boot/firmware/overlays/
   ```

3. Прописать оверлей в конфигурационном файле загрузчика `/boot/firmware/extlinux/extlinux.conf`:
   ```text
   fdtoverlays /overlays/lcd1602.dtbo
   ```

4. Перезагрузить плату:
   ```bash
   sudo reboot
   ```

   ls -l /sys/bus/i2c/devices/1-0027

# Шаг 2: Реализация I2C-обмена и инициализация HD44780

## 1. Схема распиновки PCF8574

Расширитель I2C -> 8-бит параллельного порта PCF8574 соединён с дисплеем HD44780 по следующей схеме:

* **Bit 0 (`0x01`):** `RS` (0 = команда, 1 = данные)
* **Bit 1 (`0x02`):** `RW` (0 = запись)
* **Bit 2 (`0x04`):** `E` (Enable строб: `1` -> `0` защёлкивает данные)
* **Bit 3 (`0x08`):** Подсветка (`1` = включена)
* **Bits 4–7 (`0xF0`):** Линии данных D4–D7 (4-битный режим)

---

## 2. Исходный код драйвера (`lcd1602_init.c`)

### Ограничение по выводам (Pinout)
Микросхема PCF8574T имеет всего 8 портов ввода-вывода (P0–P7). Для управления дисплеем HD44780 требуются не только линии данных, но и служебные сигналы:

- P0: RS (Register Select — выбор: команда или данные)
- P1: RW (Read/Write — обычно притянут к земле)
- P2: EN (Enable — стробирующий сигнал тактирования)
- P3: LED (Управление подсветкой экрана)
- P4–P7: Линии данных DB4, DB5, DB6, DB7

Для 8-битного режима экрану потребовалось бы 8 линий данных (DB0–DB7) и минимум 2 служебные линии (RS, EN) — итого 10 выводов. У PCF8574T их всего 8.

**Как работает полубайтовый (4-битный) режим**

Контроллер HD44780 аппаратного дисплея имеет встроенную поддержку 4-битного интерфейса. Любая передача 8-битной команды или символа разбивается на два последовательных полубайта (ниббла):
- Старший ниббл (биты 7–4): Передаются на пины P4–P7 вместе с флагами RS и LED. Подается импульс на EN для защёлкивания данных.
- Младший ниббл (биты 3–0): Сдвигаются на пины P4–P7 с теми же флагами. Подается второй импульс на EN.

Контроллер HD44780 на стороне экрана принимает эти два 4-битных фрагмента и автоматически собирает их во внутреннем буфере обратно в один 8-битный байт перед выполнением. (По самой шине I2C от BeagleY-AI к PCF8574T всегда передаются целые байты — каждый I2C-байт единовременно выставляет логические уровни сразу на всех 8 ногах P0–P7).

## 3. Функции задержки ядра (`<linux/delay.h>`)

В ядре Linux функции msleep и usleep_range из `<linux/delay.h>` предназначены для организации задержек выполнения кода с освобождением ресурсов процессора (переводом текущего процесса в состояние сна).

### `msleep(unsigned int msecs)`

**Что делает**: Переводит текущий поток в сон на указанное количество миллисекунд.

**Как работает**: Поток переводится планировщиком ядра в состояние сна (TASK_UNINTERRUPTIBLE), а процессор переключается на другие задачи (происходит контекстный переход). Реальная точность зависит от системного таймера ядра (CONFIG_HZ).

**Зачем нужен**: Используется для длительных задержек (обычно > 10 мс), где не требуется микросекундная точность. В коде инициализации HD44780 он нужен для паузы 50 мс после подачи питания и паузы 2–5 мс после команд сброса и очистки экрана (0x01).

### `usleep_range(unsigned long min, unsigned long max)`

**Что делает**: Переводит поток в сон на время в интервале от min до max микросекунд.

**Как работает**: Использует высокоточные таймеры ядра (hrtimers). Указание диапазона вместо фиксированного значения — главное требование ядра Linux для коротких задержек. Это позволяет планировщику объединять (батчить) прерывания таймеров от разных процессов в одну точку пробуждения, экономя ресурсоёмкие переключения CPU.

**Зачем нужен**: Используется для коротких паузовых интервалов (от 1 мкс до ~20 мс). В драйвере дисплея с его помощью формируется фронт стробирующего импульса Enable (линия E удерживается в 1 от 1 до 5 мкс, после чего опускается в 0) и выдерживается пауза 50–200 мкс для обработки полубайта контроллером PCF8574/HD44780.

| Функция | Диапазон времени | Механизм | В контексте прерываний / spinlock? |
| :--- | :--- | :--- | :--- |
| `udelay(us)` | < 10 мкс | Active-wait (цикл CPU) | **Да** |
| `usleep_range(min, max)` | 1 мкс – 20 мс | `hrtimers` (переход в сон) | **Нет** |
| `msleep(ms)` | > 10–20 мс | Планировщик (переход в сон) | **Нет** |

# Шаг 3: Файловый интерфейс /dev/lcd1602 (Character Device)

## 1. Концепция подсистемы miscdevice

Для предоставления пользовательскому пространству символьного устройства в `/dev/` используется легкая подсистема `miscdevice`:
* **Динамический minor-номер (`MISC_DYNAMIC_MINOR`):** ядро автоматически выделяет свободный номер устройства.
* **Права доступа (`.mode = 0666`):** разрешают запись и чтение без использования `sudo` или настройки внешних правил `udev`.
* **Безопасный обмен данными (`copy_from_user`):** корректно копирует данные из пространства пользователя (user-space) в буфер ядра (kernel-space).

## 2. Исходный код драйвера (`lcd1602_cdev.c`)

### Что означает лицензия GPL

GNU General Public License (GPL) — это свободная лицензия с принципом copyleft («вирусная» лицензия). Она предоставляет пользователям четыре ключевые свободы: запускать код в любых целях, изучать и изменять его, распространять копии, а также публиковать модифицированные версии. Главное юридическое требование GPL: если вы создаёте производный продукт на базе GPL-кода или связываете свой код с ним и распространяете его, ваш итоговый код также обязан быть открыт и распространяться под лицензией GPL.

### Зачем макрос MODULE_LICENSE("GPL") нужен в коде драйвера

В контексте разработок под Linux этот макрос не просто юридическая формальность, а прямое техническое указание для компилятора и подсистемы загрузки модулей ядра (kmod / insmod):

- **Доступ к защищенным функциям ядра (EXPORT_SYMBOL_GPL):**
Сам Linux распространяется под лицензией GPLv2. Многие подсистемы ядра экспортируют свои внутренние функции и структуры через макрос EXPORT_SYMBOL_GPL(). Если в вашем модуле нет объявления GPL-совместимой лицензии, ядро блокирует доступ к этим символам на этапе загрузки или сборки.

- **Предотвращение «загрязнения» ядра (Kernel Tainting):**
Если загрузить модуль без указания GPL (или с указанием проприетарной лицензии), ядро установит системный флаг TAINT_PROPRIETARY_MODULE. Это сигнальное предупреждение в dmesg, указывающее, что в адресное пространство ядра загружен нетривиальный/закрытый код. Разработчики ядра Linux не принимают багрепорты и дампы упавших систем, если ядро отравлено проприетарными модулями.

- **Автоматическая документация и проверка:**
Инструменты сборки ядра (kbuild) используют значение MODULE_LICENSE, чтобы формировать служебную секцию .modinfo внутри .ko-файла. По ней система утилит определяет совместимость и легитимность модуля в рантайме.

Для модулей ядра допускаются и другие GPL-совместимые строки, например "GPL v2" или "Dual BSD/GPL", но короткая запись "GPL" является стандартом по умолчанию для большинства свободных драйверов.
